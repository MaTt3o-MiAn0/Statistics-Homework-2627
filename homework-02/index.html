From wallet seed to Ethereum address

How the recovery words of a wallet become an Ethereum address, and what each standard does.

Summary

This homework follows the practical pipeline used by Ethereum wallets, from a mnemonic phrase to a checksummed address, and explains the role of each standard and primitive. It includes an interactive run of the pipeline on a public test phrase and a statistical experiment on the avalanche effect of Keccak-256. The main conclusion is that the pipeline combines several primitives, each designed for one specific task: key management, public-key cryptography, hashing and error detection.

Standards and primitives

BIP-39: mnemonic sentence and seed

BIP-39 turns random entropy into a list of words that a person can write down. For 128 bits of entropy it appends a 4-bit checksum (the first bits of the SHA-256 hash of the entropy), giving 132 bits that are split into twelve groups of 11 bits. Each group is an index into a fixed list of 2048 words. 256 bits of entropy plus an 8-bit checksum gives 24 words. The checksum lets a wallet notice a mistyped phrase, but it does not protect anything.

The seed is derived from the words with PBKDF2-HMAC-SHA512, with 2048 iterations and the salt "mnemonic" + optional passphrase. The result is 512 bits. The optional passphrase changes the seed completely, so the same words with another passphrase lead to a different wallet.

BIP-32: hierarchical deterministic (HD) key derivation

BIP-32 defines a tree of keys from one seed. The master private key and a chain code are the two halves of HMAC-SHA512("Bitcoin seed", seed). A child key is computed from the parent key, the parent chain code and an index, again with HMAC-SHA512. Indices from 2³¹ upward are hardened (written with an apostrophe): they also use the parent private key as input, so the children cannot be derived from the public parent key alone. Normal (non-hardened) children can be derived from the extended public key, which lets a website generate receiving addresses without any private key. The cost is that a leaked child private key together with the parent's extended public key reveals the parent's private key.

BIP-44: standard derivation paths

BIP-32 does not say which branch to use for what. BIP-44 fixes the structure m / purpose' / coin_type' / account' / change / address_index. Purpose is always 44', the coin type for Ethereum is 60', and the first Ethereum account uses m/44'/60'/0'/0/0. This way the same twelve words give the same addresses in every compatible wallet. MetaMask increases the last index for each new account (m/44'/60'/0'/0/1, …), while some other wallets increase the account level instead.

secp256k1: elliptic-curve public-key cryptography

secp256k1 is the curve y² = x³ + 7 over a prime field of about 2²⁵⁶ elements (p = 2²⁵⁶ − 2³² − 977), with a standard base point G of prime order n ≈ 2²⁵⁶. The private key is a number k between 1 and n − 1. The public key is the point Q = kG, which is the same operation as Homework 1, with 256-bit numbers. Recovering k from Q is the elliptic-curve discrete logarithm problem, with a best known generic attack of about 2¹²⁸ steps. The same key pair is also used to sign transactions with ECDSA.

Keccak-256: the hash function

Keccak-256 is a hash function based on the sponge construction. It maps any input to 256 bits, with an avalanche effect and no practical way to find preimages or collisions. Ethereum hashes the 64 bytes of the public key (x and y, without the leading format byte) and keeps the last 20 bytes as the address. The same function is used throughout Ethereum, for example for transaction and block hashes.

EIP-55: mixed-case checksum

An address is 40 hexadecimal characters and a typo is easy to make. EIP-55 hides a checksum in the letters (a to f) of the address, without changing its format. Take the Keccak-256 hash of the lowercase address written as text. Then for each letter of the address, write it in upper case if the corresponding hexadecimal digit of the hash is 8 or more, and in lower case otherwise. Wallets can recompute this and warn when the case does not match. An address has on average about 15 letters, so about 15 bits of checksum. EIP-55 itself estimates that a random typo passes the check with probability about 0.0247%. Fully lowercase or fully uppercase addresses are still accepted but are not protected.

The two most common confusions: key generation is the only step that needs randomness, and everything after it is deterministic, so the same words always give the same wallet. And encoding is not encryption: converting words to bits, or bytes to hexadecimal, hides nothing.

Statistical properties along the pipeline

StageProperty that matters
EntropyMust be uniformly random and unpredictable, produced by a cryptographically secure generator. A weak generator breaks everything that follows.
BIP-39 wordsA bijection from bits to words, not a random function. Words inherit the uniformity of the entropy. The checksum bits are a deterministic function of the entropy.
PBKDF2 and HMAC-SHA512Outputs behave like random bytes for anyone who does not know the input. The 2048 iterations only slow down guessing of weak phrases.
secp256k1Public keys of uniformly random private keys are uniform on the group, but they keep algebraic structure: (k₁ + k₂)G = k₁G + k₂G. There is no avalanche effect, as the toy experiments in Homework 1 show.
Keccak-256Avalanche effect: changing one input bit flips about half of the output bits. The 160-bit address looks uniformly random, and a collision would need about 2⁸⁰ tries by the birthday bound.
EIP-55The checksum bits are taken from a hash, so they are effectively random with respect to typing errors. Each letter adds about one bit.

Historical context

YearEvent
1977RSA, the first widely used public-key system (Rivest, Shamir, Adleman). Its security rests on factoring.
1985Elliptic-curve cryptography proposed independently by Koblitz and Miller. Context for secp256k1, not in the list of the assignment.
2001SHA-2 family (SHA-256, SHA-384, SHA-512) standardized by NIST. SHA-512 is used inside the BIP-39 and BIP-32 key derivation.
2009Bitcoin launches with secp256k1. Context, not in the list of the assignment.
2012BIP-32 introduces hierarchical deterministic wallets. In the same year NIST selects Keccak as the winner of the SHA-3 competition.
2013BIP-39 defines mnemonic words and the seed derivation.
2014BIP-44 defines the multi-account path structure.
2015NIST standardizes SHA-3 (FIPS 202), based on Keccak. Ethereum launches in the same year, using the original Keccak.
2016EIP-55 introduces mixed-case checksum addresses.

The order explains the design. Public-key cryptography (1977) and SHA-2 (2001) were already mature when HD wallets were designed (2012 to 2014), so BIP-32/39/44 are built on top of existing primitives such as HMAC-SHA512 and PBKDF2, together with the secp256k1 curve inherited from Bitcoin. Keccak had just won its competition when Ethereum was designed, and Ethereum adopted it before the standard was finalized. EIP-55 came last, as a backward-compatible usability fix.

The two families are related in purpose, as both are cryptographic hash functions, but they are built differently. Ethereum does not use the standardized SHA3-256 but Keccak-256. Both use the same internal permutation and the same parameters. The only difference is the padding: when NIST standardized SHA-3 it added a domain-separation suffix, which changes the first padding byte from 0x01 (original Keccak, used by Ethereum) to 0x06 (SHA3-256). The outputs are therefore completely different, even for the same input:

    Keccak-256 avalanche experiment

    A good hash function changes about half of its output bits when one input bit changes. Here the input is the 64-byte public key of the test wallet. In trial i, one bit of byte i is flipped (bit number i mod 8), Keccak-256 is recomputed and compared with the original hash: 64 trials in total.

    The modified inputs are not valid public keys, so their 160-bit suffixes are not real wallet addresses. With only 64 related inputs the results are descriptive: they illustrate the expected behavior but do not prove collision resistance or security. The entropy shown is the entropy of the share of 0 and 1 bits, not the entropy of a private key.

    The test phrase is the word "abandon" (index 0) eleven times, followed by "about" (index 3). The entropy is 128 zero bits, and the first four bits of the SHA-256 hash of 16 zero bytes (0x37) are 0011. So the last word has seven zero bits followed by the checksum 0011, which is index 3, "about".

    Why several primitives?

    Each step solves a different problem, and no single algorithm can solve all of them:

    PiecePurposeWhy another tool could not do it
    BIP-39, BIP-32, BIP-44Key management: a backup that a human can write down, and a standard tree of keys derived from itNeither a hash nor a signature scheme gives a recoverable, structured set of keys, and wallets need the same paths to be interoperable.
    secp256k1A public/private key relationship and digital signaturesA hash function cannot sign: anyone can compute a hash, so it proves nothing. Signing needs a private value that only the owner knows and a public value that anyone can verify.
    Keccak-256Hashing: compress the 64-byte public key into a short, uniform 20-byte identifierElliptic curves do not compress arbitrary data into a fixed size, and they have algebraic structure that a fingerprint should not have.
    EIP-55Checksum, error detection for typing mistakes, in a backward-compatible formatHashing and signatures are for security. A checksum is a convenience, costs no extra characters and works with old software.

    Using several simple, well-studied tools has other advantages too. Each can be analysed and replaced separately, and a weakness in one does not necessarily break the others. The pieces also come from different times and communities (Bitcoin wallets for BIP-32/39/44 and secp256k1, the SHA-3 competition for Keccak, Ethereum for EIP-55), and reusing them gave compatibility with existing hardware wallets and libraries.
